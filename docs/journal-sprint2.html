Angular

Essentiel
shareReplay(1) — Cache Observable
Évite les appels HTTP répétés quand plusieurs composants souscrivent au même Observable.
this.http.get<T>(url).pipe(shareReplay(1))
→ 1er appel : requête HTTP · Appels suivants : cache
Essentiel
Tests unitaires Jasmine — Anatomie
describe() → groupe les tests
it() → un test unitaire
beforeEach() → état propre avant chaque test
expect().toBe() → valeur exacte
expect().toEqual() → égalité profonde
💬 "J'utilise beforeEach pour garantir l'isolation — chaque test part d'un état propre."
Important
Mock dans les tests
Pas de vrais appels HTTP dans les tests — on isole avec provideHttpClientTesting().
Principe d'isolation : tester une seule chose à la fois, sans dépendances externes.
Important
Erreurs Angular — Réflexes
Could not resolve "X" → npm install X
Cannot find module → vérifier le chemin d'import
is not a known element → module non importé
💡 Lire le message mot par mot — Angular est précis.
Utile
Observable asynchrone — Piège classique
console.log après subscribe() s'exécute avant la réponse.
Toujours mettre le code qui dépend de la réponse à l'intérieur du callback subscribe.

.NET / C#

Essentiel
DI — Durées de vie (Lifetime)
AddSingleton → une instance pour toute l'app
AddScoped → une instance par requête HTTP ← DbContext
AddTransient → nouvelle instance à chaque injection
⚠️ Un Singleton ne peut pas dépendre d'un Scoped
💬 "Le DbContext est Scoped car il vit et meurt avec la requête HTTP — évite les problèmes de concurrence."
Essentiel
Pagination EF Core
Pattern standard :
query.Skip((page - 1) * pageSize).Take(pageSize)
Page 1 → Skip(0) · Page 2 → Skip(pageSize)
⚠️ Angular Paginator commence à 0, l'API à 1
→ Passer currentPage + 1 au service
Important
FindAsync vs FirstOrDefaultAsync
FindAsync(id) → vérifie le cache EF Core — plus rapide pour la clé primaire
FirstOrDefaultAsync(p => p.X == x) → toujours en BDD, flexible
✅ Clé primaire → FindAsync · Autre critère → FirstOrDefaultAsync
Important
AsQueryable() — Filtres dynamiques
Construit la requête SQL dynamiquement sans l'exécuter immédiatement.
var q = _context.Products.AsQueryable();
if (cat.HasValue) q = q.Where(...);
EF Core génère un seul SQL optimisé à la fin.
Important
Convention REST — Query params
✅ Filtres et pagination en query params :
GET /api/products/paged?page=1&pageSize=12&category=1
❌ Éviter les params dans le path pour les filtres
[FromQuery] en C# pour binder automatiquement
Utile
OnModelCreating — Toujours nécessaire
Même si la BDD existe, c'est la source de vérité :
HasPrecision, relations → schéma
HasData() → seed rejoué à chaque Update-Database
Supprimer = perdre la config au prochain clone

Git & GitHub

Essentiel
git status vs commits non pushés
git status → état des fichiers en local uniquement
"nothing to commit" ≠ "tout est sur GitHub"
Pour voir les commits non pushés :
git log origin/branch..HEAD --oneline
git status -sb → affiche "ahead X"
Essentiel
Supprimer une branche — Procédure complète
git branch -d feat/ma-branche → local
git push origin --delete feat/ma-branche → remote
git fetch --prune → nettoie les refs obsolètes
⚠️ git branch -d ne supprime PAS sur GitHub
Important

✅ Tests passent
✅ Toutes les checkboxes de l'issue cochées
✅ Code commenté supprimé
✅ console.log supprimés
⚠️ Ne pas merger si une tâche est incomplète !
Important
GitHub — Milestones = EPICs

CSS & UI

Important
rem vs px
rem → relatif à la font-size racine (16px par défaut) — s'adapte aux préférences utilisateur
px → valeur fixe absolue
✅ rem → typo, spacing, padding · ✅ px → bordures, ombres
💬 "J'utilise rem pour l'accessibilité WCAG — si l'utilisateur agrandit la police, l'UI s'adapte."
🏗️

Architecture

Important
Back-first vs Value-first
Back-first → solide, logique, testable via Swagger — rien de visible pour le client
Value-first → demo rapide — back pas prêt
✅ Règle pro : au moins une feature visible par sprint
💬 "Je construis le back en premier, mais je planifie toujours une feature visible par sprint pour rassurer le client."
Important
Filtres côté back vs front
❌ Filtres front → toutes les données en mémoire → anti-pattern
✅ Filtres back → seules les données nécessaires → scalable
10 000 produits → filtres front = explosion mémoire
10 000 produits → filtres back = SQL optimisé
💡 Règle d'or : Ce qui ne scale pas à 10 000 entrées est un anti-pattern. Toujours penser côté serveur pour les filtres et la pagination dès qu'on a une vraie BDD.
